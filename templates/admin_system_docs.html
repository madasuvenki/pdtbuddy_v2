1) Why this is not pure RAG

The application uses a hybrid chatbot architecture. Vector search is useful for semantic lookup, but the CR domain is highly structured and must stay numerically correct. For counts, filters, trends, and per-target answers, deterministic SQL is safer than pure embedding-based retrieval.

  • SQL first for exact metrics, counts, filter logic, and target-specific queries.
  • Vector / semantic search only for fuzzy lookup, title similarity, and chatbot-style fallback.
  • LLM formats answers and helps interpret intent; it does not directly write to the DB.

4) Why each table was created

  • dashboard_status keeps target metadata centralized so the app never has to guess active targets or prefixes.
  • cr_master makes cross-target CR queries fast and predictable.
  • cr_relationships stores related CR networks so sibling / regression relationships are queryable.
  • target_summary gives the UI and chatbot a single daily snapshot for charts and headline metrics.
  • orbit_cr_cache reduces latency and external API pressure by caching CR details.
  • cr_master_search supports semantic retrieval and chatbot RAG-like fallback without polluting the transactional tables.

5) Relationship map

  • dashboard_status tells ingest which target is active and which BU schema to use.
  • <db_name>_unique_crs is the source input for the central tables.
  • cr_master is the main query table for chatbot and reports.
  • cr_relationships is derived from mapped_cr in the raw BU table.
  • target_summary is aggregated from raw BU CR + JIRA tables.
  • orbit_cr_cache enriches detail views and chatbot responses.
  • cr_master_search is the semantic retrieval layer for vector / RAG-style lookup.

6) Sync cycle

  1. Excel ingestion loads BU tables.
  2. Central sync refreshes cr_master, cr_relationships, and target_summary.
  3. Orbit cache is refreshed on demand when CR detail is fetched.
  4. The chatbot first tries exact SQL or cached detail, then semantic retrieval when appropriate.
