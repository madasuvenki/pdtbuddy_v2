Endpoint 0 — Team Selection NEW

Why the team matters — read this first

The team decides which Axiom test-case vector database is searched. Pick the wrong team and the API does not fail — it returns confident but wrong test-case suggestions, which then feed straight into the TEA you post to Orbit.

That is why team_name is required and validated on /api/v1/chat. Only one of the 1580 real taxonomy teams is accepted; anything else is rejected with a 400 and a list of suggestions.

The two-step flow

  1. Discover — GET /api/v1/teams?search=kernel to find your exact team path
  2. Select — POST /api/v1/select-team to save it as your default

Then pass that exact team_name on every /api/v1/chat call. Selecting a default is convenient, but the chat endpoint still requires the field explicitly — so a wrong team can never be used silently, even if you never called select-team.

GET /api/v1/teams — list valid teams

GET /api/v1/teams

Returns the valid Axiom taxonomy teams. There are ~1580, so the response is searchable and paginated rather than one huge list.

Query paramTypeRequiredDescription
search string Optional Case-insensitive substring filter, e.g. kernel. Use this — it is far easier than paging 1580 entries.
username string Optional Marks your currently-selected team with is_current: true and echoes it as current_team.
has_vector_db boolean Optional true returns only teams that already have a test-case vector DB built — i.e. teams that can actually return suggestions today.
limit integer Optional Page size. Default 100, maximum 500, 0 = no limit.
offset integer Optional Pagination offset. Default 0.

Example — find every Kernel team that has a vector DB

curl -G https://tea-assistant.qualcomm.com/api/v1/teams \
  --data-urlencode "search=platform/kernel" \
  --data-urlencode "username=your-username" \
  --data-urlencode "has_vector_db=true"
200 Success Response
{
  "status": "success",
  "total": 18,
  "returned": 3,
  "offset": 0,
  "limit": 100,
  "search": "platform/kernel",
  "current_team": "APT/Platform/Kernel",
  "teams": [
    {
      "team_name": "APT/Platform/Kernel",
      "has_vector_db": true,
      "is_current": true
    },
    {
      "team_name": "APT/XR/Platform/Kernel",
      "has_vector_db": true,
      "is_current": false
    },
    {
      "team_name": "APT/CSE_Test/Platform/Kernel",
      "has_vector_db": true,
      "is_current": false
    }

total is the full match count (so you know whether to page); returned is how many are in this page.

Check has_vector_db before you commit

A team can be perfectly valid yet have has_vector_db: false, meaning nobody has built its test-case database yet. Test-case suggestions will be empty until someone creates it from the web UI (database icon → Create Vector DB).

POST /api/v1/select-team — save your default

POST /api/v1/select-team

Validates a team and saves it as your default. Authentication is identical to the chat endpoints (see Authentication).

ParameterTypeRequiredDescription
username string Required Your Qualcomm username. Must be on the TEA-Assistant list.
team_name string Required A valid team path from GET /api/v1/teams, e.g. APT/Platform/Kernel. Case-insensitive and a leading / is tolerated, but the path itself must be exact.
api_key string Optional* Your QGenie API key. Required only if you have never saved one. See API Key Setup.

Request

curl -X POST https://tea-assistant.qualcomm.com/api/v1/select-team \
  -H "Content-Type: application/json" \
  -d '{
    "username": "your-username",
    "team_name": "APT/Platform/Kernel"
  }'
200 Success
{
  "status": "success",
  "username": "your-username",
  "team_name": "APT/Platform/Kernel",
  "requested": null,
  "has_vector_db": true,
  "warning": null
}

requested is non-null when your input was normalised — send apt/platform/kernel and you get back "team_name": "APT/Platform/Kernel" with "requested": "apt/platform/kernel", so you can see exactly what was stored.

200 Valid team, but no vector DB yet
{
  "status": "success",
  "team_name": "APT/XR/CPT/Kernel",
  "has_vector_db": false,
  "warning": "Team 'APT/XR/CPT/Kernel' is valid, but no test-case vector database has been created for it yet, so test-case suggestions will be empty. Create it from the TEA Assistant web UI (database icon → Create Vector DB)."
}

Still a 200 — the team is real and has been saved. The warning tells you now, rather than letting you wonder later why suggestions are empty.

400 Invalid team — with suggestions
{
  "error": "'APT/Kernel' is not a valid team.",
  "hint": "Use GET /api/v1/teams?search= to find the exact team path, then pass it as 'team_name'.",
  "valid_team_count": 1580,
  "suggestions": [
    "APT/XR/CPT/Kernel",
    "APT/Platform/Kernel",
    "APT/XR/Platform/Kernel",
    "APT/Aluminum/Platform/Kernel",
    "APT/CSE_Test/Platform/Kernel"
  ]
}

Every rejection includes suggestions, so a typo is one copy-paste away from being fixed instead of a dead end.

What counts as a valid team

  • Full path required — APT/Platform/Kernel, not just Kernel. A bare leaf is rejected because "Kernel" exists under many different parents, and guessing one is exactly how you get wrong test cases.
  • Case-insensitive — apt/platform/kernel resolves to APT/Platform/Kernel.
  • Separators are forgiving — a leading/trailing /, doubled // and backslashes are all normalised.
  • Organisational roots are not teams — APT or MPSS alone are rejected: they have no Axiom taxonomy id, so no vector DB can exist for them.

Python — discover, then select

import requests

BASE = "https://tea-assistant.qualcomm.com"
USER = "your-username"

# 1. Find the exact team path — filter to teams that can actually
#    return suggestions today.
r = requests.get(f"{BASE}/api/v1/teams", params={
    "search": "platform/kernel",
    "username": USER,
    "has_vector_db": "true",
}, timeout=30)
r.raise_for_status()
teams = r.json()

print(f"{teams['total']} matching teams:")
for t in teams["teams"]:
    print("  ", t["team_name"], "(current)" if t["is_current"] else "")

# 2. Save the one you want as your default.
chosen = teams["teams"][0]["team_name"]
r = requests.post(f"{BASE}/api/v1/select-team",
                  json={"username": USER, "team_name": chosen}, timeout=30)
if r.status_code == 400:
    # Never a dead end — the error carries suggestions.
    err = r.json()
    print("Invalid:", err["error"])
    print("Did you mean:", err.get("suggestions"))
else:
    r.raise_for_status()
    result = r.json()
    print("Selected:", result["team_name"])
    if result.get("warning"):
        print("WARNING:", result["warning"])

# 3. From now on pass this exact value as team_name on /api/v1/chat.

  5. Once approved, you can use the API with your Qualcomm username
Join TEA-Assistant List

Authentication

The API uses two layers of authentication: list membership (who can call the API) and QGenie API key (which LLM to use for analysis).

Authentication Flow

  1. Include your Qualcomm username in the request JSON
  2. The API validates your membership in the TEA-Assistant LDAP list
  3. If not a member → 403 Forbidden
  4. The API resolves your QGenie API key (payload → DB → error)
  5. If no API key found → 400 Bad Request
  6. If all checks pass, the CR is analyzed using your key and model

API Key Setup

Each user needs a QGenie API key to use this endpoint. The key is resolved in this priority order:

1
api_key in payload — Used immediately and saved to database for future calls
Best for first-time use or key rotation
2
Previously saved key — Your key was saved on a prior call or via the web UI settings
🔒 Stored securely encrypted per-user — only used for your own requests, never shared
✗
Neither found — Returns 400 error
Must provide api_key in payload or set via web UI first

Option A: Set via Web UI (Recommended)

Log in to the TEA Assistant web interface and set your API key once — it will be saved for all future API calls:

  1. Go to https://10.213.98.5:5001
  2. Click the ⚙️ gear icon in the top-right header
  3. Enter your QGenie API key and select your preferred model
  4. Click Save Settings
  5. Your key is now saved — API calls with your username will use it automatically

Option B: Pass in Payload (First Call)

Include api_key in your first request — it will be saved automatically for future calls:

{
  "message": "12345678",
  "username": "your-username",
  "api_key": "your-qgenie-api-key",
  "stream": false
}

After this call, subsequent requests do not need to include api_key — it will be retrieved from the database automatically.

Security Note

Your API key is stored securely encrypted in the database, tied only to your username. It is never shared with other users and is only used to process your own requests.

Updating Your API Key

To update your key, simply pass the new api_key in any request — it will overwrite the saved key in the database.

Streaming with EventSource

function streamCRAnalysis(crNumber, username) {
  // First make the POST request to start streaming
  fetch('/api/cr-summary', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      message: crNumber,
      username: username,
      stream: true
    })
  }).then(response => {
    const reader = response.body.getReader();
    const decoder = new TextDecoder();
    
    function readStream() {
      reader.read().then(({ done, value }) => {
        if (done) {
          console.log('Stream complete');
          return;
        }
        
        const chunk = decoder.decode(value);
        const lines = chunk.split('\n');
        
        lines.forEach(line => {
          if (line.startsWith('data: ')) {
            const data = JSON.parse(line.slice(6));
            if (data.content === '[DONE]') {
              console.log('Analysis complete');
            } else {
              process.stdout.write(data.content);
            }
          }
        });
        
        readStream();
      });
    }
    
    readStream();
  });
}

Python Example

import requests
import json

def analyze_cr(cr_number, username, stream=False):
    url = "https://tea-assistant.qualcomm.com/api/cr-summary"
    
    payload = {
        "message": str(cr_number),
        "username": username,
        "stream": stream
    }
    
    headers = {
        "Content-Type": "application/json"
    }
    
    if stream:
        # Streaming request
        response = requests.post(url, json=payload, headers=headers, stream=True)
        
        if response.status_code == 200:
            for line in response.iter_lines():
                if line:
                    line = line.decode('utf-8')
                    if line.startswith('data: '):
                        data = json.loads(line[6:])
                        if data.get('content') == '[DONE]':
                            break
                        print(data.get('content', ''), end='')
        else:
            print(f"Error: {response.status_code}")
    else:
        # Non-streaming request
        response = requests.post(url, json=payload, headers=headers)
        
        if response.status_code == 200:
            data = response.json()
            print("Analysis:", data['content'])
            return data
        else:
            print(f"Error: {response.status_code}")
            return None

# First call — provide api_key (saved automatically for future calls)
result = analyze_cr(12345678, "your-username", api_key="your-qgenie-api-key")

# Subsequent calls — api_key is optional (retrieved from database)
result = analyze_cr(12345678, "your-username")

Endpoint 2 — Chat API (Multi-Turn) NEW

POST /api/v1/chat

The full conversational TEA Assistant, exposed as an API. This is the same engine that powers the web chat UI — identical turn planning, root cause analysis, TEA generation and entity memory. Only the authentication differs.

What you can do with it

  • Analyse a CR or SR — send the number, get a full root cause analysis
  • Ask follow-up questions — "what is the jira for this?", "show me the gerrit change"
  • Get test-case suggestions from your team's Axiom vector database
  • Generate a TEA — category, analysis details and mitigation details
  • Confirm with "yes" — the assistant remembers the question it asked
  • Switch CRs mid-conversation — it detects this and asks how to proceed

Base URL

https://tea-assistant.qualcomm.com

Same authentication as CR Summary

This endpoint uses exactly the same two checks described in Authentication and API Key Setup: TEA-Assistant list membership (→ 403 if not a member) and a QGenie API key (→ 400 if none found). A key you already saved via the web UI or a previous /api/cr-summary call works here too.

Chat API — Request Parameters

Request Body (JSON)

Parameter Type Required Description
username string Required Your Qualcomm username. Must be a member of the TEA-Assistant list.
message string Required Your message for this turn. Can be a CR number ("3148333"), a natural-language request ("analyse CR 3148333"), a follow-up question ("what is the jira?") or a confirmation ("yes").
session_id string Optional* Send the SAME value on every turn to enable follow-up questions. Any string works — a UUID, a ticket id, "jenkins-job-42". If omitted, a throwaway id is generated and the conversation has no memory. See Sessions & Follow-ups.
api_key string Optional* Your QGenie API key. Required on first use if you have never saved one; it is then persisted for future calls. See API Key Setup.
team_name string Required Axiom taxonomy team used for test-case lookup, e.g. APT/Platform/Kernel. Must be a valid team — invalid values are rejected with a 400 and suggestions. Find yours with GET /api/v1/teams.

Why required? The team selects which vector DB is searched, so a wrong team returns confident but wrong test cases. Making it explicit means that can never happen silently. The canonical form is also saved as your default.
inputType string Optional "cr" (default) or "sr" — how to interpret a bare number.
stream boolean Optional true (default) returns an SSE stream. false returns one complete JSON body — recommended for scripts and automation.

Chat API — Sessions & Follow-ups

Conversation state is keyed on username + session_id in Redis — not on a browser cookie. That is what makes multi-turn conversations work for an API client, and why it works correctly across all server replicas.

You must supply and re-use your own session_id

If you omit session_id, every request is an isolated cold start — the assistant will not remember the CR you were discussing, so "what is the jira for this?" cannot be answered. Generate one id per conversation and send it with every turn.

What is remembered between turns

CapabilityMeaning
Entity memory The current CR/SR is remembered, so "this CR", "the jira", "the gerrit change" all resolve.
Conversation history Previous turns are included as context, and are also saved to your History sidebar in the web UI.
Pending confirmations When the assistant asks "Do you want to post this TEA?", a bare "yes" on the next turn is understood as the answer.
CR-switch detection Mention a different CR and it asks whether to start fresh or switch this conversation over.

How long a session lasts

  • 7 days of sliding expiry in Redis — the timer resets on every use, so an active conversation never expires mid-use
  • After that, the conversation is rehydrated from PostgreSQL and live Orbit data is re-fetched — so an old session_id still works
  • session_id is scoped per username, so two users can both use "session-1" without collision

Python — a reusable conversation client

import uuid
import requests

BASE_URL = "https://tea-assistant.qualcomm.com"


class TeaChat:
    """
    A multi-turn TEA Assistant conversation.

    One TeaChat instance == one conversation. The session_id is generated once
    and re-used for every message, which is what gives you follow-up memory.
    """

    def __init__(self, username, team_name, api_key=None, session_id=None):
        self.username = username
        # REQUIRED on every request — the team selects which vector DB is
        # searched, so it is never inferred.
        self.team_name = team_name
        self.api_key = api_key
        # Generate ONCE and keep it — this is the conversation's identity.
        self.session_id = session_id or f"py-{uuid.uuid4()}"

    def send(self, message, timeout=600):
        payload = {
            "username": self.username,
            "team_name": self.team_name,     # required every turn
            "session_id": self.session_id,
            "message": message,
            "stream": False,
        }
        # api_key only needs to be sent until it is saved server-side.
        if self.api_key:
            payload["api_key"] = self.api_key

        r = requests.post(f"{BASE_URL}/api/v1/chat", json=payload, timeout=timeout)
        if r.status_code == 400:
            err = r.json()
            # An invalid team always comes back with suggestions.
            if err.get("suggestions"):
                raise ValueError(f"{err['error']} Did you mean: {err['suggestions']}")
            raise ValueError(err.get("error", r.text))
        r.raise_for_status()
        return r.json()


# ── Usage ────────────────────────────────────────────────────────────────────
chat = TeaChat(
    username="your-username",
    team_name="APT/Platform/Kernel",     # from GET /api/v1/teams
    api_key="your-qgenie-api-key",       # needed only on the first ever call
)

# Turn 1 — root cause analysis
print(chat.send("3148333")["content"])

# Turn 2 — follow-up; "this" resolves because the session is the same
print(chat.send("what is the jira for this?")["content"])

# Turn 3 — TEA generation
result = chat.send("generate TEA for this CR")
print(result["content"])
if result.get("tea_data"):
    print("Category:", result["tea_data"].get("AnalysisCategory"))

# Turn 4 — confirm the pending question
print(chat.send("yes")["content"])

Python — consuming the SSE stream

import json
import requests

def stream_chat(username, session_id, message, api_key=None):
    payload = {
        "username": username,
        "session_id": session_id,
        "message": message,
        "stream": True,
    }
    if api_key:
        payload["api_key"] = api_key

    with requests.post(
        "https://tea-assistant.qualcomm.com/api/v1/chat",
        json=payload, stream=True, timeout=600
    ) as r:
        r.raise_for_status()
        for line in r.iter_lines():
            if not line:
                continue
            line = line.decode("utf-8")
            if not line.startswith("data: "):
                continue
            event = json.loads(line[6:])

            if event.get("content") == "[DONE]":
                break
            if event.get("content"):
                print(event["content"], end="", flush=True)
            if event.get("tea_data"):
                print("\n\n[TEA]", event["tea_data"])


stream_chat("your-username", "my-session-1", "3148333",
            api_key="your-qgenie-api-key")

const sessionId = `js-${crypto.randomUUID()}`;

async function sendChat(message, { username, apiKey, teamName } = {}) {
  const body = {
    username,
    session_id: sessionId,   // same id every turn -> follow-ups work
    message,
    stream: false
  };
  if (apiKey)   body.api_key   = apiKey;
  if (teamName) body.team_name = teamName;

  const res = await fetch('https://tea-assistant.qualcomm.com/api/v1/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(body)
  });

  if (!res.ok) {
    const err = await res.json().catch(() => ({}));
    throw new Error(err.error || `HTTP ${res.status}`);
  }
  return res.json();
}

// Multi-turn usage
const opts = { username: 'your-username', apiKey: 'your-qgenie-api-key',
               teamName: 'APT/Platform/Kernel' };

const turn1 = await sendChat('3148333', opts);
console.log(turn1.content);

const turn2 = await sendChat('what is the jira for this?', opts);
console.log(turn2.content);

Set a generous client timeout

Root cause analysis and TEA generation invoke an LLM and can run for a minute or more. The server allows up to 600 seconds, so set your HTTP client timeout to 600 to avoid a client-side timeout on a request that would otherwise have succeeded.

Endpoint 3 — Gerrit Chat API NEW

POST /api/v1/gerrit-chat

The Gerrit code-review assistant, exposed as an API. Send a Gerrit change number and it fetches the live code diff and commit message, then explains the purpose, the key changes, and the risk/impact. Follow-up questions work exactly like the Chat API.

Why this is a separate endpoint

Gerrit chat is a different assistant, not a mode of the TEA one. It uses a different system prompt (code-review expert rather than TEA analyst) and writes to a separate conversation history. Merging it into /api/v1/chat would put Gerrit reviews into your TEA history and distort the dashboard CR counts — so it gets its own URL while sharing the identical authentication.

What you can do with it

  • Summarise a code change — send the Gerrit change number
  • Understand the purpose — what problem the change is solving
  • Review key changes — the significant edits in the diff
  • Assess risk & impact — what could regress
  • Ask follow-ups — "is this change risky?", "which files changed?", "any concerns with error handling?"

No team_name needed here

Unlike /api/v1/chat, this endpoint does not require team_name — it only reads the Gerrit code diff and never searches the Axiom test-case vector database, so there is no team-specific data involved.

Request Body (JSON)

Parameter Type Required Description
username string Required Your Qualcomm username. Must be a member of the TEA-Assistant list.
message string Required A Gerrit change number ("3456789") to analyse, or a follow-up question about the change already in this session.
session_id string Optional* Send the SAME value on every turn to enable follow-up questions. Omitted → a throwaway id, so no memory. Same semantics as the Chat API — see Sessions & Follow-ups.
api_key string Optional* Your QGenie API key. Required on first use if you have never saved one. See API Key Setup.
stream boolean Optional true (default) returns an SSE stream. false returns one complete JSON body.

Response format is identical to the Chat API — see Chat API — Response Formats. The tea_data and choices fields are always null here, since Gerrit chat does not generate TEA or offer switch choices.

Python — Gerrit review client

import uuid
import requests

BASE_URL = "https://tea-assistant.qualcomm.com"


class GerritChat:
    """
    A multi-turn Gerrit code-review conversation.

    Identical pattern to TeaChat — one instance == one conversation, and the
    session_id is generated once so follow-up questions keep the diff context.
    """

    def __init__(self, username, api_key=None, session_id=None):
        self.username = username
        self.api_key = api_key
        self.session_id = session_id or f"gerrit-{uuid.uuid4()}"

    def send(self, message, timeout=600):
        payload = {
            "username": self.username,
            "session_id": self.session_id,
            "message": message,
            "stream": False,
        }
        if self.api_key:
            payload["api_key"] = self.api_key

        r = requests.post(f"{BASE_URL}/api/v1/gerrit-chat",
                          json=payload, timeout=timeout)
        r.raise_for_status()
        return r.json()


# ── Usage ────────────────────────────────────────────────────────────────────
review = GerritChat(username="your-username",
                    api_key="your-qgenie-api-key")   # first call only

# Turn 1 — summarise the change
print(review.send("3456789")["content"])

# Turn 2 — follow-up; the diff is still in context
print(review.send("what is the risk of this change?")["content"])

Separate conversation history

Gerrit conversations are saved to the Gerrit History sidebar in the web UI, not the TEA one. A session_id used with /api/v1/gerrit-chat is tracked independently from one used with /api/v1/chat, so re-using the same string across both endpoints will not share context.

Analysing an SR instead of a CR

The Chat API handles SRs (customer service requests) as well as CRs — just set inputType to "sr" so a bare number is read as an SR: 

curl -X POST https://tea-assistant.qualcomm.com/api/v1/chat \
  -H "Content-Type: application/json" \
  -d '{
    "username": "your-username",
    "session_id": "sr-session-1",
    "message": "5012345",
    "inputType": "sr",
    "stream": false
  }'

You can also just name it in natural language — "analyse SR 5012345" — and it is detected automatically regardless of the inputType setting. Follow-up questions then work the same way as for a CR.

Conversation issues that are not HTTP errors

These return 200 with an explanatory content message rather than an error status:

SymptomCause & fix
Follow-up questions are not understood You did not re-use the same session_id. Generate one per conversation and send it on every turn — see Sessions & Follow-ups.
"Please give me a CR number first" This session has no CR yet. Send the CR number before asking for TEA or test cases.
"I could not find CR <number>" The CR does not exist in Orbit, or is not accessible. Check the number — it must be digits only.
"Gerrit change <number> could not be found" /api/v1/gerrit-chat only: the change id does not exist or the diff is not retrievable. Verify the numeric Gerrit change id.
"No relevant testcase found since vector db not created" No vector DB exists for that team. Create it from the web UI (database icon → Create Vector DB) and verify your team_name spelling.
"RATE_LIMIT_EXCEEDED" Your QGenie quota was hit. Retry later, or switch model in the web UI settings.
Client-side timeout Your HTTP timeout is too low for an LLM call. Raise it to 600 seconds.

Error Handling Best Practices

  • Always check the HTTP status code before processing the response
  • Implement proper error handling for network timeouts
  • For streaming requests, handle connection drops gracefully
  • Log errors for debugging purposes
  • Provide user-friendly error messages in your application
